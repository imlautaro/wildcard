## Configuración

```jsonc [apps/api/wrangler.jsonc]
"d1_databases": [
  {
    "binding": "DB",
    "database_name": "wildcard-db",
    "database_id": "<installation-specific>",
    "migrations_dir": "migrations"
  }
]
```

Todo lo que guarda el producto vive en esta única base de datos SQLite: cuentas y sesiones, contactos, chats, grupos, memoria, tareas, documentos, miniapps, conectores, el feed Para ti, outboxes y la configuración de administración. Las marcas de tiempo están en milisegundos.

## Patrón de acceso

- **SQL directo.** La API usa `env.DB.prepare(...)`, `.bind()` y `env.DB.batch([...])` con SQL escrito a mano. Drizzle (`src/db/schema.ts`) solo lo usa el adaptador de Better Auth.
- **Batches atómicos y guardas.** La publicación, los claims de atención y las revisiones del historial se basan en sentencias condicionales `INSERT … SELECT` / `UPDATE … WHERE` dentro de batches, en lugar de bloqueos en la aplicación.
- **Triggers.** Varias invariantes se garantizan con triggers, por ejemplo el registro de instancias de Workflow (`register_private_workflow`) y el llenado del outbox `resource_cleanup` cuando se eliminan filas.
- **Límite de SELECT compuestos.** D1 limita las sentencias `SELECT` compuestas a cinco términos; valida el SQL inusual contra D1 local en `workerd` (consulta las verificaciones estáticas en `scripts/checks/`).

## Migraciones

- `apps/api/migrations` contiene **93** archivos secuenciales, desde `0001_auth.sql` hasta `0093_privacy_controls.sql`.
- Las migraciones son aditivas y solo hacia adelante. **Nunca reescribas una migración ya aplicada.** Una reversión del Worker no deshace los cambios en D1, así que cada migración debe seguir siendo compatible con el Worker activo en ese momento.
- En local: `npm run auth:setup:local` (la primera vez) o `npm run db:migrate:local`.
- En producción: el script de release de la API ejecuta `wrangler d1 migrations apply DB --remote` **antes** de subir el código nuevo. No hay un paso manual de migración aparte.

Consulta [Migraciones de base de datos](/es/operations/database-migrations) para ver el flujo para agregar una.

## Búsqueda de texto completo

Los contactos buscan en conversaciones pasadas con tablas virtuales **FTS5** de SQLite (`chat_turn_search` desde la migración 0007, `group_message_search` desde la 0019). La selección de memoria es léxica por defecto; el ranking semántico opcional guarda los embeddings de Workers AI en la propia D1 (migración 0057) en lugar de usar Vectorize.

## Rate limits en D1

Los endpoints de autenticación usan buckets fijos de un minuto con clave en un SHA-256 de `ip:path:bucket` en `auth_rate_limit`, con la IP del cliente tomada de `CF-Connecting-IP`. El mismo helper limita otras acciones por usuario (por ejemplo, la generación en chats a 20 por minuto). Superar un límite devuelve `429`.

## Outbox de limpieza

Eliminar un chat, un contacto, un grupo o una cuenta no puede borrar de forma síncrona los objetos de R2 ni las instancias de Workflow. En su lugar, triggers de D1 encolan filas en `resource_cleanup` (migración 0063, acotada por la 0064). La tarea `cleanResources` del Cron de cada minuto lo vacía con reintentos y backoff. Las pruebas de ciclo de vida en `apps/api/tests` cubren estos caminos.

## Inspeccionar la base de datos

```bash [Terminal]
# Base de datos local
cd apps/api && npx wrangler d1 execute DB --local --command "SELECT COUNT(*) FROM user"
```

::caution
No consultes datos de producción para validar funciones. Usa datos locales ficticios. En esta instalación, `wrangler d1 … --remote` no está autorizado para el login local de Wrangler; el estado de las migraciones remotas se infiere a partir de un release exitoso de la API.
::
