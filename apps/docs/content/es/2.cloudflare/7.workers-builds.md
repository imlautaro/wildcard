Los releases de producción son **automáticos**: cada Worker tiene su propio proyecto de Workers Builds conectado al repositorio de GitHub y a la rama `main`. Un push a `main` compila y despliega los Workers cuyas rutas vigiladas cambiaron. Ningún proyecto necesita editar archivos versionados: el release de la API resuelve la cuenta, D1, R2 y los orígenes en el momento del release (consulta [Aprovisionamiento](/es/operations/provisioning#qué-resuelve-el-release)). Para la API y la app web, el workflow opcional de GitHub Actions es una alternativa; usa solo uno de los dos por Worker.

## Proyectos

| Worker | Raíz | Comando de build | Comando de deploy | Previews |
| --- | --- | --- | --- | --- |
| `wildcard-api` | `/` | `npm ci && npm run typecheck` | `npm run release:ci` | Desactivadas |
| `wildcard-web` | `/` | `npm ci && npm run typecheck:web && npm run build:web` | `npm run release:web` | Activadas: `npm run preview:web` |
| `wildcard-admin` | `/` | `npm ci && npm run typecheck:admin && npm run build:admin` | `npm run release:admin` | Desactivadas |
| `wildcard-site` | `/` | `npm ci && npm run typecheck:site && npm run build:site` | `npm run release:site` | Desactivadas |
| `wildcard-docs` | `/` | `npm ci && npm run typecheck:docs && npm run build:docs` | `npm run release:docs` | Desactivadas |

La raíz del build siempre es `/` porque los workspaces de npm usan el lockfile de la raíz y Nuxt resuelve la capa compartida desde ahí.

## Watch paths

Cada proyecto solo compila cuando cambian sus entradas. `docs/workers-build-paths.json` es la referencia para la configuración del dashboard (Wrangler no lo lee).

| Worker | Rutas incluidas (además de las entradas de build de la raíz) |
| --- | --- |
| `wildcard-api` | `apps/api/*`, `shared/*`, `scripts/release-worker.mjs`, `scripts/lib/*`, `apps/web/wrangler.jsonc` (el nombre del Worker web define el `MCP_WEB_ORIGIN` predeterminado) |
| `wildcard-web` | `apps/web/*`, `packages/ui/*`, `shared/*`, `scripts/release-web.mjs`, `scripts/preview-web.mjs`, `scripts/lib/*` |
| `wildcard-admin` | `apps/admin/*`, `packages/ui/*`, `scripts/release-admin.mjs`, `scripts/lib/*` |
| `wildcard-site` | `apps/site/*`, `packages/ui/*`, `scripts/release-site.mjs`, `scripts/lib/*` |
| `wildcard-docs` | `apps/docs/*`, `scripts/release-docs.mjs`, `scripts/lib/*` |

Entradas de build de la raíz vigiladas por todos los proyectos: `package.json`, `package-lock.json`, `.nvmrc`, `.npmrc`, `.gitignore`. Por lo tanto, un cambio en el lockfile vuelve a compilar todos los Workers.

El `*` de las watch paths de Cloudflare coincide con directorios anidados (no es un glob del sistema de archivos). Los filtros se omiten en los pushes sin archivos modificados, con 3.000 archivos o más, o con 20 commits o más.

## Protecciones del release

Cada script de release (`scripts/release-*.mjs`) se niega a ejecutarse a menos que:

1. se ejecute en CI: `WORKERS_CI=1` (Workers Builds) o `GITHUB_ACTIONS=true` (el workflow de deploy de GitHub Actions);
2. la rama (`WORKERS_CI_BRANCH` o `GITHUB_REF_NAME`) sea igual a la rama de producción (`main`, o `WILDCARD_PRODUCTION_BRANCH`);
3. el commit (`WORKERS_CI_COMMIT_SHA` o `GITHUB_SHA`) sea un SHA completo igual a `git rev-parse HEAD`;
4. el checkout esté limpio (`git status --porcelain` está vacío).

Las protecciones están en `scripts/lib/release-guard.mjs`. `npm run release:check` informa en cuáles se detendría un release real, sin detenerse.

Luego despliega con `wrangler deploy --tag <commit SHA>`, de modo que la versión activa siempre se puede rastrear hasta su commit de origen. El primer build después de conectar un repositorio puede no tener los metadatos de origen y detenerse de forma segura; el siguiente push hace el release.

## Secretos de build

Solo el proyecto de la API tiene secretos de build: `META_API_KEY` y los valores opcionales `ELEVENLABS_API_KEY`, `APNS_*` y `VAPID_*`, todos guardados como variables de build **cifradas**. Las variables de build sin cifrar solo hacen falta para cambiar los valores predeterminados: `CLOUDFLARE_ACCOUNT_ID` (cuando la credencial ve varias cuentas), `WILDCARD_API_URL`, `WILDCARD_WEB_URL`, `WILDCARD_SUPER_ADMIN_USER_IDS`, `WILDCARD_DB_NAME` y `WILDCARD_PHOTOS_BUCKET`. Los valores vacíos cuentan como no definidos. El release de la API los copia a secretos de runtime mediante un archivo temporal accesible solo por su propietario, que se pasa a `wrangler deploy --secrets-file` y se elimina en un bloque `finally`. Consulta [Releases](/es/operations/releases).

## Credenciales

| Proyecto | Permisos mínimos |
| --- | --- |
| API | Edición de Workers Scripts, edición de D1, edición de Workflows, edición de R2 (el primer release crea el bucket), lectura de la cuenta |
| Web, admin, site, docs | Edición de Workers Scripts y lectura de la cuenta |

Selecciona en el dashboard una credencial existente con el alcance adecuado; nunca hagas commit de su valor.

## Verificar un release

```bash [Terminal]
# Check runs publicados por Workers Builds en un commit
gh api repos/<owner>/<repo>/commits/<sha>/check-runs \
  --jq '.check_runs[] | "\(.name)|\(.status)|\(.conclusion)"'

# Versiones activas de un Worker y sus tags (tag = SHA del commit)
npx wrangler deployments list --config apps/site/wrangler.jsonc
```
