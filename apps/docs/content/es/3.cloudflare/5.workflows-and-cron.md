## Por qué Workflows

Una respuesta puede tardar minutos: el contacto espera mientras la persona escribe, lee, piensa, llama herramientas, investiga en la web, genera imágenes y publica varias burbujas con un ritmo humano. Cloudflare Workflows le da a cada uno de estos trabajos **pasos duraderos** (`step.do`) con reintentos y timeouts, y **esperas duraderas** (`step.sleep`), de modo que el trabajo continúa cuando la aplicación está cerrada y se reanuda tras los fallos sin repetir los pasos ya completados.

```jsonc [apps/api/wrangler.jsonc]
"workflows": [
  { "name": "wildcard-onboarding", "binding": "ONBOARDING_WORKFLOW", "class_name": "OnboardingWorkflow" },
  { "name": "wildcard-chat", "binding": "CHAT_WORKFLOW", "class_name": "ChatWorkflow" }
]
```

Los nombres de los Workflows son globales en la cuenta: una instalación independiente debe elegir sus propios nombres y conservar los bindings y los nombres de clase. Wrangler crea o actualiza ambos Workflows y el Cron Trigger durante el release normal de la API.

## `ChatWorkflow`

`apps/api/src/chat/workflow.ts` enruta según el tipo de payload:

| Tipo | Handler | Iniciado por |
| --- | --- | --- |
| Turno privado (por defecto) | Pipeline de respuesta | `POST …/chat/turns` → `dispatchAgent` |
| `group` | Ronda de respuestas en grupo (`groups/workflow.ts`) | Mensajes de grupo, solicitudes, bienvenidas |
| `initiative` | Mensajes proactivos y reenganche (`chat/initiative.ts`) | Cron `dispatchInitiatives` |
| `welcome` | Primer mensaje de un contacto nuevo (`chat/welcome.ts`) | Cron `dispatchContactWelcomes` |
| `home` | Curaduría de Para ti (`home/workflow.ts`) | Cron `dispatchHome` o `/api/v1/home/refresh` |
| `home-comment` | Respuestas del contacto a comentarios de Para ti | Creación de comentarios |

Los turnos de trabajo de tareas, las programaciones y los despertares de los monitores de páginas también se ejecutan como instancias de `CHAT_WORKFLOW`.

### Pasos principales de una respuesta privada

`select-account-model` → `check-attention` → `attended-chat` (breve demora de conexión) → espera al compositor → `batch-consecutive-messages` → `mark-running` → `read-delay` → `mark-read` → `transcribe-voice` opcional → actualización de memoria → `prepare-reply` (hasta 2 reintentos, timeout de 8 minutos) → `reply-timing-decision` → para cada burbuja `compose-message-N`, `voice-message-N` opcional, `publish-message-N` → `deliver-push` → actualización de memoria → `review-conversation-learning` → `release-attention` → presencia inactiva.

Los IDs de instancia son deterministas (por ejemplo `chat-<turnID>-a1`) y se registran en `chat_workflow_instance` antes de crearse, para que la recuperación siempre pueda encontrarlos, reintentarlos o limpiarlos.

### Atención

Un agente atiende un elemento a la vez entre todos sus chats privados y grupos. `agent_attention` guarda un claim atómico, garantizado por un trigger; cuando un Workflow termina, `release-attention` despacha el siguiente elemento en cola. El Cron libera los claims abandonados.

## `OnboardingWorkflow`

Se inicia con el ID `onboarding-<owner>` después del registro (`POST /api/v1/onboarding`):

1. `load-preferences` y `generate-identities` (Muse Spark planifica cinco contactos).
2. `adult-birthday-plan` y `publish-contacts` (los contactos aparecen de inmediato con `setup_pending = 1`).
3. Pasos `adult-portrait-N-*` en paralelo generan retratos con `muse-image-1.0` en R2, con un fallback `ready-without-portrait`.
4. `publish-circle` crea el grupo opcional Friends, Study o Work y completa el onboarding.

La misma clase ejecuta los trabajos de **generación de contactos con IA** cuando el payload incluye un `generationID`.

## El Cron de cada minuto

`* * * * *` llama a `scheduled()` en `apps/api/src/index.ts`. Cada tarea se ejecuta en `ctx.waitUntil` y es idempotente.

| Grupo | Tareas |
| --- | --- |
| Recuperación | `recoverOnboarding`, `recoverContactGeneration`, `recoverChats` (concilia los turnos con el estado del Workflow, hasta 50 por ejecución), `recoverGroups` |
| Despacho | `dispatchSchedules`, `dispatchTasks`, `dispatchMonitors`, `dispatchHome`, `dispatchInitiatives`, `dispatchContactWelcomes`, `dispatchWelcomes`, `dispatchGroupRequests` |
| Entrega | `deliverPush` (outbox de APNs/Web Push), `deliverGroupPush`, `deliverRemoteNative` |
| Limpieza | `cleanResources` (outbox de R2 y Workflows), `cleanAttachments`, `cleanOAuthFlows`, `prunePersonalityEvents` (60 días), `pruneLearning`, `expirePresence`, `expireLinkPreviews` |

La Energía no tiene tarea de Cron: los saldos se recargan de forma diferida cuando una admisión en un grupo los verifica.

## Manejo de fallos

- Los errores de modelo conocidos (`MODEL_*`) activan una fase acotada de `recover-response`; los demás fallos se guardan en el turno para que el cliente pueda ofrecer un reintento (`POST …/turns/:turnID/retry`).
- Las herramientas iniciadas conservan sus comprobantes, así que los reintentos no repiten efectos secundarios.
- Workers Logs muestra solo eventos saneados. Las instancias que ya están en ejecución conservan la versión del código y el modelo con los que empezaron.
