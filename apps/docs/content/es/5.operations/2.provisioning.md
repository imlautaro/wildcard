Los archivos de Wrangler versionados son neutrales respecto de la cuenta: no contienen `account_id`, ni un ID real de D1, ni URLs de la instalación, ni IDs de administradores. Un fork se despliega **sin editar ningún archivo versionado**. En el momento del release, `scripts/release-worker.mjs` resuelve la instalación para la cuenta de destino en el archivo ignorado `apps/api/wrangler.release.json`, y el primer release crea la base de datos D1 y el bucket de R2 privado. La versión canónica y más detallada es `docs/infrastructure.md`.

## Qué resuelve el release

| Valor | Origen |
| --- | --- |
| Cuenta de Cloudflare | `CLOUDFLARE_ACCOUNT_ID`; si no está, la única cuenta que puede ver la credencial |
| Base de datos D1 | Se busca por nombre (`wildcard-db`, o `WILDCARD_DB_NAME`); se crea si no existe |
| Bucket de R2 | `wildcard-contact-photos` (o `WILDCARD_PHOTOS_BUCKET`), privado; se crea si no existe |
| `BETTER_AUTH_URL` | `WILDCARD_API_URL`; si no está, `https://wildcard-api.<subdomain>.workers.dev` |
| `MCP_WEB_ORIGIN` | `WILDCARD_WEB_URL`; si no está, `https://wildcard-web.<subdomain>.workers.dev` |
| `SUPER_ADMIN_USER_IDS` | `WILDCARD_SUPER_ADMIN_USER_IDS` (vacía: nadie puede usar el panel de administración) |

`<subdomain>` es el subdominio `workers.dev` de la cuenta. Los valores vacíos en CI cuentan como no definidos. `BETTER_AUTH_SECRET` se genera solo en el primer release y se conserva después.

## Requisitos previos

- Una cuenta de Cloudflare con Workers, D1, R2 y Workflows disponibles en su plan, y un subdominio `workers.dev` (abrir **Workers & Pages** una vez en el dashboard lo crea), salvo que definas tanto `WILDCARD_API_URL` como `WILDCARD_WEB_URL`.
- Un fork (o una copia) de este repositorio en GitHub.
- Una clave de la Meta Model API con acceso a Muse Spark 1.3 y Muse Voice Transcribe.
- Opcional: clave de ElevenLabs, cuenta de Apple Developer (APNs, App Groups, Associated Domains), claves VAPID (`node scripts/generate-vapid-keys.mjs`).
- Opcional, para revisar la cuenta antes del primer push: Node.js 24+ y `npx wrangler login`.

## Opcional: revisa la cuenta primero

Ambos comandos usan tu login local de Wrangler y nunca despliegan, migran ni editan archivos versionados:

```bash [Terminal]
npm run release:check                 # simulación: cuenta, orígenes, D1, R2 y secretos faltantes
npm run infra:provision               # muestra los recursos; -- --create crea D1 y R2 ahora
```

Es opcional, porque el primer release crea por sí mismo los recursos que faltan. `npm run infra:photos` es un alias de `infra:provision`.

## Despliega la API y la app web

Elige **una sola** de estas opciones por instalación. Si usas dos para los mismos Workers, se publican dos veces.

::tabs
  :::tabs-item{label="Deploy to Cloudflare"}
  [![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/imlautaro/wildcard)

  El botón copia el repositorio en tu cuenta de GitHub (un repositorio nuevo con un solo commit "source repo import", no un fork) y crea un proyecto de Workers Builds conectado al Worker `wildcard-api`. Su comando de deploy, `npm run deploy`, publica la API y luego compila y publica la app web, así que ambos Workers salen de ese único proyecto.

  En el formulario:

  - Mantén el nombre de Worker **`wildcard-api`**. El service binding de la app web apunta a él; un proyecto renombrado falla con un mensaje que lo indica.
  - Ingresa `META_API_KEY`. El formulario pide cada clave del `.env.example` de la raíz; se guarda como secret del Worker `wildcard-api` y los releases la conservan.
  - Mantén los comandos precargados: build `npm run build`, deploy `npm run deploy`.

  Para las voces de los contactos, agrega después `ELEVENLABS_API_KEY` como secret del Worker `wildcard-api` (**Settings → Variables and secrets**). A partir de ahí, cada push a `main` del repositorio nuevo publica ambos Workers. El primer build es lento (unos dos minutos, todas las migraciones) y las respuestas pueden tardar durante los primeros minutos después de él; consulta [Solución de problemas](/es/operations/troubleshooting).
  :::

  :::tabs-item{label="GitHub Actions"}
  `.github/workflows/deploy.yml` se activa de forma explícita. En cada push a `main` (o en una ejecución manual) comprueba los tipos, publica la API y luego compila y publica la app web. No publica el panel de administración, el sitio ni la documentación, y no compila Previews de ramas.

  En el fork, abre **Settings → Secrets and variables → Actions** y agrega:

  | Tipo | Nombre | Obligatorio |
  | --- | --- | --- |
  | Variable | `WILDCARD_DEPLOY` = `true` | Sí (activa el workflow) |
  | Secreto | `CLOUDFLARE_API_TOKEN` | Sí |
  | Secreto | `META_API_KEY` | Sí |
  | Secreto | `ELEVENLABS_API_KEY`, `APNS_*`, `VAPID_*` | Opcionales (cada grupo, completo o vacío) |
  | Variable | `CLOUDFLARE_ACCOUNT_ID` | Cuando el token puede ver varias cuentas |
  | Variable | `WILDCARD_API_URL`, `WILDCARD_WEB_URL`, `WILDCARD_SUPER_ADMIN_USER_IDS` | Opcionales |

  Crea el token de API desde la plantilla **Edit Cloudflare Workers**, agrega **Account → D1 → Edit** y limítalo a tu cuenta (no hacen falta zonas). Nunca hagas commit de su valor.

  Haz push a `main` o ejecuta manualmente el workflow **Deploy**. La primera ejecución crea D1, R2, ambos Workers, los Workflows y el trigger de Cron.
  :::

  :::tabs-item{label="Workers Builds"}
  Conecta al fork un proyecto de Workers Builds por Worker, rama `main`, raíz `/`:

  - **API** (`wildcard-api`): build `npm ci && npm run typecheck`, deploy `npm run release:ci`, previews desactivadas. Credencial: edición de Workers Scripts, edición de D1, edición de Workflows, edición de R2 y lectura de la cuenta. Agrega el secreto de build cifrado `META_API_KEY` (y los opcionales `ELEVENLABS_API_KEY`, `APNS_*`, `VAPID_*`). Agrega `CLOUDFLARE_ACCOUNT_ID`, `WILDCARD_API_URL`, `WILDCARD_WEB_URL` o `WILDCARD_SUPER_ADMIN_USER_IDS` como variables de build solo cuando los necesites.
  - **Web** (`wildcard-web`), una vez que exista la API: build `npm ci && npm run typecheck:web && npm run build:web`, deploy `npm run release:web`. Credencial: edición de Workers Scripts y lectura de la cuenta. Para las Previews por rama, habilita los builds que no son de producción con el comando de preview `npm run preview:web`.

  Copia las rutas de inclusión de `docs/workers-build-paths.json` en **Settings → Builds** de cada proyecto y elimina el `*` predeterminado (consulta los [watch paths](/es/cloudflare/workers-builds#watch-paths)). Haz push de un commit: el release de la API crea D1 y R2 si hace falta, migra D1, genera `BETTER_AUTH_SECRET`, sube los secretos y publica la API con sus Workflows y su Cron.
  :::
::

## Verifica

```bash [Terminal]
npm run smoke -- https://wildcard-web.<subdomain>.workers.dev
```

La prueba de humo registra una cuenta descartable, crea un contacto, envía un mensaje y espera la respuesta del modelo, lo que demuestra que el proxy web, la autenticación, D1, los Workflows y `META_API_KEY` funcionan juntos. La cuenta creada permanece; elimínala desde la configuración de Cuenta de la app. Consulta [Releases](/es/operations/releases#verificar-un-release) para las comprobaciones que no necesitan una cuenta.

## Pasos opcionales

::steps{level="3"}

### Panel de administración, sitio y docs

Crea un proyecto de Workers Builds para cada uno con los comandos de [Workers Builds](/es/cloudflare/workers-builds#proyectos) (el workflow de GitHub Actions no los publica). Para dar acceso de administración, inicia sesión en el origen de admin, copia tu ID de usuario de la pantalla "Not a super admin" en `WILDCARD_SUPER_ADMIN_USER_IDS` (variable de GitHub o variable de build de la API) y vuelve a publicar la API. Define las URLs del sitio en `apps/site/app/utils/site.ts` y la URL de la documentación en `apps/docs/nuxt.config.ts`.

### AI Gateway

`npm run infra:ai-gateway -- --create`; luego define `AI_GATEWAY_ID` y haz push una vez verificado.

### App de iOS

Equipo de firma, bundle IDs, `WILDCARD_API_URL`, `WILDCARD_APP_GROUP`, `WILDCARD_LINK_HOST`, capacidades y clave de APNs (consulta [App de iOS](/es/apps/ios#configuración-para-tu-propia-cuenta)).
::

::warning
`WILDCARD_SUPER_ADMIN_USER_IDS` se aplica en cada release de la API. Si la eliminas o la dejas vacía, el siguiente release revoca todo el acceso de administración.
::

## Staging

No existe un entorno de staging. Una configuración de staging necesita sus propios nombres de Worker, base de datos D1, bucket de R2, nombres de Workflow, secretos, orígenes y configuración de iOS. Nunca apuntes las Previews ni staging a la base de datos de producción sin querer (las Previews web usan actualmente la API de producción por diseño).
