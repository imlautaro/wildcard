## La regla

Los releases de producción salen **solo** del código fuente commiteado y pusheado en `main`, compilado y desplegado por CI: Cloudflare Workers Builds o el workflow opcional de GitHub Actions `.github/workflows/deploy.yml` (solo la API y la app web). Usa uno de los dos por Worker. Consulta [Aprovisionamiento](/es/operations/provisioning#despliega-la-api-y-la-app-web) para configurar cualquiera de ellos. No ejecutes `wrangler deploy` ni `wrangler secret put` a mano para saltarte el pipeline; investiga los fallos. Las excepciones (como los primeros releases manuales de los sitios estáticos) debe aprobarlas el propietario y deben quedar registradas en `docs/infrastructure.md`.

## Flujo

::steps{level="3"}

### Commit y push a `main`

Workers Builds inicia un build para cada Worker cuyos [watch paths](/es/cloudflare/workers-builds#watch-paths) coinciden con el cambio. El workflow de GitHub Actions, cuando está activado con `WILDCARD_DEPLOY=true`, se ejecuta en cada push a `main` y publica la API y luego la app web.

### Build

`npm ci` desde el lockfile raíz, la verificación de tipos del Worker y su build (`nuxt build` / `nuxt generate`; la API no tiene un paso de empaquetado separado antes del deploy).

### Script de release

`npm run release:<worker>` comprueba las [protecciones del release](/es/cloudflare/workers-builds#protecciones-del-release) y despliega con `--tag <commit SHA>`.

### Verificación

Revisa el check run de Workers Builds (o la ejecución **Deploy** de GitHub Actions) en el commit y el tag de la versión activa (ver más abajo).
::

## Release de la API (`scripts/release-worker.mjs`)

1. Protecciones: CI (Workers Builds o GitHub Actions), rama de producción, checkout limpio, `HEAD` igual al commit que disparó el CI (`WORKERS_CI_COMMIT_SHA` o `GITHUB_SHA`).
2. Resuelve la instalación en el archivo ignorado `apps/api/wrangler.release.json`: cuenta, D1 por nombre, bucket de R2 privado (ambos se crean en el primer release), `BETTER_AUTH_URL`, `MCP_WEB_ORIGIN` y `SUPER_ADMIN_USER_IDS` (consulta [Aprovisionamiento](/es/operations/provisioning#qué-resuelve-el-release)). Nunca edita archivos versionados.
3. Aplica las **migraciones remotas de D1** antes de publicar el código.
4. Lista solo los **nombres** de los secretos existentes del Worker (ninguno antes del primer release).
5. Si `BETTER_AUTH_SECRET` no existe, genera 48 bytes aleatorios; después nunca lo vuelve a generar. Toma `META_API_KEY` y los opcionales `ELEVENLABS_API_KEY`, `APNS_*` y `VAPID_*` del entorno de CI. Los valores vacíos cuentan como no definidos, así que se ignoran los secretos que GitHub Actions pasa como cadenas vacías. Un `META_API_KEY` ausente tanto en CI como en runtime, o un grupo `APNS_*` o `VAPID_*` incompleto, detiene el release.
6. Los escribe en un archivo JSON accesible solo para el propietario en un directorio temporal privado, ejecuta `wrangler deploy --secrets-file … --tag <sha>` y elimina el archivo en un bloque `finally`. Los valores nunca aparecen en argumentos ni en logs.
7. Wrangler también crea o actualiza ambos Workflows y el Cron Trigger.

## Releases de web, admin, sitio y docs

| Script | Despliega |
| --- | --- |
| `release-web.mjs` | `apps/web/.output/server/wrangler.json` (generado por Nitro) |
| `release-admin.mjs` | `apps/admin/.output/server/wrangler.json` |
| `release-site.mjs` | `apps/site/wrangler.jsonc` (assets en `.output/public`) |
| `release-docs.mjs` | `apps/docs/wrangler.jsonc` (assets en `.output/public`) |

Las mismas protecciones, sin secretos y sin migraciones. La cuenta sale de `CLOUDFLARE_ACCOUNT_ID` o de la única cuenta de la credencial.

## Simulación

```bash [Terminal]
npm run release:check
```

Ejecuta el release de la API con `--dry-run` en cualquier lugar con un login de Wrangler (o un `CLOUDFLARE_API_TOKEN` limitado): muestra la cuenta, los orígenes, D1 y R2 resueltos, lo que crearía el primer release, en qué protecciones se detendría un release real y los **nombres** de los secretos que subiría. Nunca crea, migra ni despliega.

## Rotación de secretos

Actualiza la variable de build cifrada en la configuración de Workers Builds de la API (o el secreto de GitHub Actions) y haz push de un commit autorizado. El release sube el nuevo valor junto con el código.

::warning
`BETTER_AUTH_SECRET` existe solo en runtime. Rotarlo (o eliminar y volver a crear el Worker) cierra la sesión de todos y hace que las credenciales almacenadas de los conectores MCP no se puedan descifrar.
::

## Verificar un release

```bash [Terminal]
# Check runs: wildcard-api, wildcard-web, wildcard-admin, … en el commit pusheado
gh api repos/<owner>/<repo>/commits/<sha>/check-runs \
  --jq '.check_runs[] | "\(.name)|\(.status)|\(.conclusion)"'

# El tag de la versión activa debe ser igual al SHA del commit
npx wrangler deployments list --config apps/api/wrangler.jsonc
```

Comprobación de punta a punta a través de la app web (registra una cuenta descartable, crea un contacto y espera una respuesta del modelo; después elimina la cuenta desde la configuración de Cuenta):

```bash [Terminal]
npm run smoke -- https://<web>
```

Comprobaciones rápidas que no necesitan datos de cuentas:

| Comprobación | Resultado esperado |
| --- | --- |
| `GET https://<api>/api/v1/me` | `401` JSON |
| `GET https://<api>/unknown` | `404` JSON |
| `GET https://<api>/api/v1/admin/session` | `404` (admin es privado) |
| `GET https://<web>/api/v1/me` | `401` JSON a través del proxy |
| `GET https://<admin>/api/v1/admin/session` | `401` |
| `GET https://<docs>/` | `302` a `/en` |

Los check runs aparecen solo cuando un build termina. Un run exitoso de `wildcard-api` implica que sus migraciones se aplicaron (el release las ejecuta primero).

## Rollback

- **Código**: vuelve a una versión anterior del Worker en el dashboard, o haz push de un revert. Prefiere avanzar con una corrección cuando una versión más nueva repara datos.
- **Datos**: las migraciones no se revierten. Mantén las tablas y columnas aditivas; el código anterior las ignora. El rollback de un Worker nunca restaura filas de D1 ni objetos de R2 eliminados.
- **Web, admin, sitio y docs** no almacenan datos; hacerles rollback o eliminarlos es seguro. Mantén los contratos de la API compatibles con iOS y web, porque los clientes y la API se publican de forma independiente.
- Las instancias de Workflow que ya están en ejecución conservan la versión y el modelo con los que iniciaron.
