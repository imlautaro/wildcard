## Vista general del sistema

```text
            iPhone app (SwiftUI)                      Browser
                    │                                    │
                    │ HTTPS + Authorization: Bearer      │ HTTPS + httpOnly cookie
                    │                                    ▼
                    │                    ┌──────────────────────────────┐
                    │                    │ wildcard-web (Nuxt 4 SPA)    │
                    │                    │ /api/v1/* proxy              │
                    │                    └──────────────┬───────────────┘
                    │                                   │ service binding API
                    ▼                                   ▼
  ┌──────────────────────────────────────────────────────────────────────┐
  │ wildcard-api (Hono + Better Auth)                                    │
  │   fetch      → /api/v1/*                                             │
  │   scheduled  → minute Cron (dispatch, recovery, cleanup, push)       │
  │   ChatWorkflow, OnboardingWorkflow (Cloudflare Workflows)            │
  │   AdminAPI   → named entrypoint, reachable only by service binding   │
  └───┬────────────┬─────────────┬───────────────┬───────────────────────┘
      │            │             │               │
      ▼            ▼             ▼               ▼
  D1 (DB)     R2 (CONTACT_    Workers AI (AI)  External: Meta Model API,
  wildcard-db  PHOTOS)        embeddings and   ElevenLabs, APNs, Web Push,
               private media  AI Gateway       remote MCP servers
                    ▲
  ┌─────────────────┴──────────────┐      ┌──────────────────────────────┐
  │ wildcard-admin (Nuxt 4 SPA)    │      │ wildcard-site, wildcard-docs │
  │ binding API → entrypoint       │      │ static assets only           │
  │ AdminAPI                       │      └──────────────────────────────┘
  └────────────────────────────────┘
```

Ideas clave:

- **Una sola API es dueña de todo.** Solo `wildcard-api` tiene D1, R2, Workflows, Cron, Workers AI y secretos. Los Workers web y de administración no tienen datos ni secretos; reenvían las solicitudes mediante **service bindings**.
- **Sesiones Bearer en todas partes.** La API solo acepta tokens `Authorization: Bearer` firmados por Better Auth. iOS guarda el token en el Keychain; el proxy web lo guarda en una cookie `httpOnly` y agrega el header. Por eso la API no necesita CORS.
- **Trabajo durable en Workflows.** Las respuestas, las rondas de grupo, el onboarding, la generación de contactos, el trabajo de tareas y el feed Para ti se ejecutan como instancias de Workflow, así que sobreviven al cierre de la app y se reintentan paso a paso.
- **Un Cron de cada minuto es la red de seguridad.** Recupera despachos atascados, envía mensajes programados, inicia turnos de iniciativa y de tareas, reintenta la entrega de push y vacía el outbox de limpieza.
- **Los clientes hacen polling.** No hay WebSocket ni SSE. El chat visible consulta su página más reciente cada segundo; las listas y los feeds consultan con menos frecuencia y solo mientras están visibles.

## Vida de un mensaje privado

::steps{level="3"}

### El cliente envía un turno

`POST /api/v1/contacts/:id/chat/turns` con un UUID generado por el cliente, el texto (1–4000 caracteres) y, opcionalmente, un adjunto, una nota de voz, un sticker o una respuesta con cita. Reintentar con el mismo ID devuelve el turno existente, así que los envíos son idempotentes. Los adjuntos se escriben en R2 bajo `attachments/{owner}/{contact}/{turn}/{uuid}`.

### La API lo guarda y responde 202

El turno se inserta en `chat_turn` con estado `queued`, protegido por el `history_revision` del chat y un límite de 10 turnos en cola o en ejecución. Un trigger de D1 registra la futura instancia de Workflow en `chat_workflow_instance`. La respuesta incluye el turno y la presencia del contacto.

### El despacho reclama la atención del agente

En `waitUntil`, `dispatchAgent` (`apps/api/src/chat/dispatch.ts`) reclama de forma atómica al agente en `agent_attention` (un turno a la vez por agente, compartido entre chats privados y grupos) y crea la instancia de `CHAT_WORKFLOW`.

### `ChatWorkflow` prepara la respuesta

`apps/api/src/chat/workflow.ts` selecciona el modelo de la cuenta, espera brevemente mientras la persona sigue escribiendo, combina mensajes consecutivos, marca el turno como leído, transcribe las notas de voz, actualiza la memoria y ejecuta `prepare-reply`: un bucle de herramientas de hasta tres rondas contra la API Chat Completions de Meta (`apps/api/src/chat/meta.ts`). Las herramientas incluyen búsqueda en memoria y en mensajes, programaciones, tareas, documentos, investigación web, herramientas MCP, generación de imágenes y miniapps.

### Las burbujas se publican a ritmo humano

Cada respuesta tiene de una a ocho burbujas. Para cada una, el Workflow marca al contacto como *escribiendo* (o *grabando* para una respuesta de voz), espera una pausa proporcional a la longitud, opcionalmente sintetiza voz con ElevenLabs y agrega la burbuja a D1 en un batch. Las notificaciones push se encolan en un outbox.

### Cierre y recuperación

El Workflow entrega los push (APNs y Web Push), actualiza la memoria, ejecuta una revisión silenciosa de aprendizaje de la conversación, libera la atención del agente (despachando el siguiente elemento en cola) y deja que la presencia quede inactiva. Si algo se atasca, `recoverChats` del Cron de cada minuto concilia el turno con el estado del Workflow.

### El cliente la ve

El chat abierto consulta `GET /api/v1/contacts/:id/chat/turns`, que devuelve los turnos, la presencia y `historyRevision`.
::

## Grupos

Un mensaje humano en un grupo inicia una **ronda de respuestas** acotada. Un coordinador (`apps/api/src/groups/planning.ts`) elige qué contactos responden; hasta cuatro pueden prepararse a la vez y la publicación es atómica respecto de una marca de agua del historial, así que los borradores desactualizados se revisan o se descartan. Cada contacto gasta **energía** (50 puntos, uno por mensaje publicado en el grupo, uno recuperado cada cinco minutos) y cada intercambio tiene un tope de 100 mensajes de bots. Consulta [Conversaciones](/es/features/conversations).

## Propiedad y aislamiento de los datos

- Cada consulta está acotada al dueño de la sesión. Los contactos compartidos le dan a cada participante una conversación privada aislada.
- La memoria está acotada por **audiencia**: lo que un contacto aprende en un chat solo viaja a donde lo permiten las reglas de privacidad ([Memoria y privacidad](/es/features/memory-and-privacy)).
- Los chats que usan conectores MCP quedan aislados de forma permanente de la memoria entre chats y siempre usan el modelo Estándar.
- Eliminar chats, contactos o cuentas escribe en un outbox `resource_cleanup` que el Cron vacía, eliminando objetos de R2 e instancias de Workflow de forma asíncrona.
