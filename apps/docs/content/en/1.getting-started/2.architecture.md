## System overview

```text
            iPhone app (SwiftUI)                      Browser
                    │                                    │
                    │ HTTPS + Authorization: Bearer      │ HTTPS + httpOnly cookie
                    │                                    ▼
                    │                    ┌──────────────────────────────┐
                    │                    │ wildcard-web (Nuxt 4 SPA)    │
                    │                    │ /api/v1/* proxy              │
                    │                    └──────────────┬───────────────┘
                    │                                   │ service binding API
                    ▼                                   ▼
  ┌──────────────────────────────────────────────────────────────────────┐
  │ wildcard-api (Hono + Better Auth)                                    │
  │   fetch      → /api/v1/*                                             │
  │   scheduled  → minute Cron (dispatch, recovery, cleanup, push)       │
  │   ChatWorkflow, OnboardingWorkflow (Cloudflare Workflows)            │
  │   AdminAPI   → named entrypoint, reachable only by service binding   │
  └───┬────────────┬─────────────┬───────────────┬───────────────────────┘
      │            │             │               │
      ▼            ▼             ▼               ▼
  D1 (DB)     R2 (CONTACT_    Workers AI (AI)  External: Meta Model API,
  wildcard-db  PHOTOS)        embeddings and   ElevenLabs, APNs, Web Push,
               private media  AI Gateway       remote MCP servers
                    ▲
  ┌─────────────────┴──────────────┐      ┌──────────────────────────────┐
  │ wildcard-admin (Nuxt 4 SPA)    │      │ wildcard-site, wildcard-docs │
  │ binding API → entrypoint       │      │ static assets only           │
  │ AdminAPI                       │      └──────────────────────────────┘
  └────────────────────────────────┘
```

Key ideas:

- **One API owns everything.** Only `wildcard-api` has D1, R2, Workflows, Cron, Workers AI and secrets. The web and admin Workers have no data and no secrets; they forward requests through **service bindings**.
- **Bearer sessions everywhere.** The API only accepts `Authorization: Bearer` tokens signed by Better Auth. iOS keeps the token in the Keychain; the web proxy keeps it in an `httpOnly` cookie and adds the header. The API therefore needs no CORS.
- **Durable work in Workflows.** Replies, group rounds, onboarding, contact generation, task work and the For you feed run as Workflow instances, so they survive the app closing and retry step by step.
- **A minute Cron is the safety net.** It recovers stalled dispatches, sends scheduled messages, starts initiative and task turns, retries push delivery and drains the cleanup outbox.
- **Clients poll.** There is no WebSocket or SSE. The visible chat polls its latest page every second; lists and feeds poll less often and only while visible.

## Life of a private message

::steps{level="3"}

### The client sends a turn

`POST /api/v1/contacts/:id/chat/turns` with a client-generated UUID, the text (1–4000 characters) and optional attachment, voice note, sticker or quoted reply. Retrying the same ID returns the existing turn, so sends are idempotent. Attachments are written to R2 under `attachments/{owner}/{contact}/{turn}/{uuid}`.

### The API stores it and answers 202

The turn is inserted into `chat_turn` with status `queued`, guarded by the chat's `history_revision` and a limit of 10 queued or running turns. A D1 trigger registers the future Workflow instance in `chat_workflow_instance`. The response carries the turn and the contact's presence.

### Dispatch claims the agent's attention

In `waitUntil`, `dispatchAgent` (`apps/api/src/chat/dispatch.ts`) atomically claims the agent in `agent_attention` (one turn at a time per agent, shared across private chats and groups) and creates the `CHAT_WORKFLOW` instance.

### `ChatWorkflow` prepares the reply

`apps/api/src/chat/workflow.ts` selects the account's model, waits briefly while the person is still typing, merges consecutive messages, marks the turn as read, transcribes voice notes, refreshes memory and runs `prepare-reply`: a tool loop of up to three rounds against the Meta Chat Completions API (`apps/api/src/chat/meta.ts`). Tools include memory and message search, schedules, tasks, documents, web research, MCP tools, image generation and mini apps.

### Bubbles are published with human pacing

Each reply has one to eight bubbles. For each one the Workflow marks the contact as *typing* (or *recording* for a voice reply), sleeps for a length-aware pause, optionally synthesizes speech with ElevenLabs and appends the bubble to D1 in a batch. Push notifications are queued in an outbox.

### Wrap-up and recovery

The Workflow delivers push (APNs and Web Push), refreshes memory, runs a silent conversation-learning review, releases the agent's attention (dispatching the next queued item) and lets presence go idle. If anything stalls, the minute Cron's `recoverChats` reconciles the turn with the Workflow status.

### The client sees it

The open chat polls `GET /api/v1/contacts/:id/chat/turns`, which returns the turns, presence and `historyRevision`.
::

## Groups

A human message in a group starts a bounded **reply round**. A coordinator (`apps/api/src/groups/planning.ts`) chooses which contacts answer; up to four can prepare at once and publication is atomic against a history watermark, so stale drafts are reviewed or dropped. Each contact spends **energy** (50 points, one per published group message, one recovered every five minutes) and every exchange has a 100-bot-message ceiling. See [Conversations](/en/features/conversations).

## Data ownership and isolation

- Every query is scoped by the session owner. Shared contacts give each participant an isolated private conversation.
- Memory is scoped by **audience**: what a contact learns in one chat only travels where the privacy rules allow ([Memory and privacy](/en/features/memory-and-privacy)).
- Chats that use MCP connectors are permanently isolated from cross-chat memory and always use the Standard model.
- Deleting chats, contacts or accounts writes to a `resource_cleanup` outbox that the Cron drains, removing R2 objects and Workflow instances asynchronously.
