## The rule

Production releases come **only** from committed and pushed source on `main`, built and deployed by CI: Cloudflare Workers Builds, or the opt-in GitHub Actions workflow `.github/workflows/deploy.yml` (API and web app only). Use one of them per Worker. See [Deploy your own](/en/self-host/deploy) to set either up. Do not run `wrangler deploy` or `wrangler secret put` by hand to bypass the pipeline; investigate failures instead. Exceptions (such as the first manual releases of the static sites) must be approved by the owner and recorded in `docs/infrastructure.md`.

## Flow

::steps{level="3"}

### Commit and push to `main`

Workers Builds starts a build for each Worker whose [watch paths](/en/cloudflare/workers-builds#watch-paths) match the change. The GitHub Actions workflow, when enabled with `WILDCARD_DEPLOY=true`, runs on every push to `main` and releases the API, then the web app.

### Build

`npm ci` from the root lockfile, the Worker's type check and its build (`nuxt build` / `nuxt generate`; the API has no separate bundling step before deploy).

### Release script

`npm run release:<worker>` checks the [release guards](/en/cloudflare/workers-builds#release-guards) and deploys with `--tag <commit SHA>`.

### Verify

Check the Workers Builds check run (or the GitHub Actions **Deploy** run) on the commit and the active version's tag (see below).
::

## API release (`scripts/release-worker.mjs`)

1. Guards: CI (Workers Builds or GitHub Actions), production branch, clean checkout, `HEAD` equal to the commit CI was triggered for (`WORKERS_CI_COMMIT_SHA` or `GITHUB_SHA`).
2. Resolves the installation into the ignored `apps/api/wrangler.release.json`: account, D1 by name, private R2 bucket (both created on the first release), `BETTER_AUTH_URL`, `MCP_WEB_ORIGIN` and `SUPER_ADMIN_USER_IDS` (see [How it works](/en/self-host/how-it-works#what-the-release-resolves)). Versioned files are never edited.
3. Applies **remote D1 migrations** before publishing code.
4. Lists only the **names** of existing Worker secrets (none before the first release).
5. If `BETTER_AUTH_SECRET` does not exist, generates 48 random bytes; it is never regenerated afterwards. Collects `META_API_KEY` and the optional `ELEVENLABS_API_KEY`, `APNS_*` and `VAPID_*` from the CI environment. Empty values count as unset, so secrets that GitHub Actions passes as empty strings are ignored. A `META_API_KEY` missing both in CI and at runtime, or an incomplete `APNS_*` or `VAPID_*` group, stops the release.
6. Writes them to an owner-only JSON file in a private temporary directory, runs `wrangler deploy --secrets-file … --tag <sha>` and deletes the file in a `finally` block. Values never appear in arguments or logs.
7. Wrangler also creates or updates both Workflows and the Cron Trigger.

## Web, admin, site and docs releases

| Script | Deploys |
| --- | --- |
| `release-web.mjs` | `apps/web/.output/server/wrangler.json` (generated by Nitro) |
| `release-admin.mjs` | `apps/admin/.output/server/wrangler.json` |
| `release-site.mjs` | `apps/site/wrangler.jsonc` (assets in `.output/public`) |
| `release-docs.mjs` | `apps/docs/wrangler.jsonc` (assets in `.output/public`) |

Same guards, no secrets, no migrations. The account comes from `CLOUDFLARE_ACCOUNT_ID` or the credential's only account.

## Dry run

```bash [Terminal]
npm run release:check
```

Runs the API release with `--dry-run` anywhere with a Wrangler login (or a scoped `CLOUDFLARE_API_TOKEN`): it prints the resolved account, origins, D1 and R2, what the first release would create, which guards a real release would stop at and the **names** of the secrets it would upload. It never creates, migrates or deploys.

## Rotating secrets

Update the encrypted build variable in the API's Workers Builds settings (or the GitHub Actions secret) and push an authorized commit. The release uploads the new value with the code.

::warning
`BETTER_AUTH_SECRET` is runtime-only. Rotating it (or deleting and recreating the Worker) signs everyone out and makes stored MCP connector credentials undecryptable.
::

## Verifying a release

```bash [Terminal]
# Check runs: wildcard-api, wildcard-web, wildcard-admin, … on the pushed commit
gh api repos/<owner>/<repo>/commits/<sha>/check-runs \
  --jq '.check_runs[] | "\(.name)|\(.status)|\(.conclusion)"'

# The active version's tag must equal the commit SHA
npx wrangler deployments list --config apps/api/wrangler.jsonc
```

End-to-end check through the web app (signs up a throwaway account, creates a contact and waits for a model reply; delete the account afterwards from Account settings):

```bash [Terminal]
npm run smoke -- https://<web>
```

Smoke checks that need no account data:

| Check | Expected |
| --- | --- |
| `GET https://<api>/api/v1/me` | `401` JSON |
| `GET https://<api>/unknown` | `404` JSON |
| `GET https://<api>/api/v1/admin/session` | `404` (admin is private) |
| `GET https://<web>/api/v1/me` | `401` JSON through the proxy |
| `GET https://<admin>/api/v1/admin/session` | `401` |
| `GET https://<docs>/` | `302` to `/en` |

Check runs appear only when a build completes. A successful `wildcard-api` run implies its migrations applied (the release runs them first).

## Rollback

- **Code**: roll back to a previous Worker version in the dashboard, or push a revert. Prefer rolling forward when a newer version repairs data.
- **Data**: migrations are not rolled back. Keep additive tables and columns; older code ignores them. Worker rollback never restores deleted D1 rows or R2 objects.
- **Web, admin, site, docs** store no data; rolling them back or deleting them is safe. Keep API contracts compatible for both iOS and web, because clients and API release independently.
- Already-running Workflow instances keep the version and model they started with.
