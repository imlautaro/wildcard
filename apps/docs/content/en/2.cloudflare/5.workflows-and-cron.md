## Why Workflows

A reply can take minutes: the contact waits while the person types, reads, thinks, calls tools, researches the web, generates images and publishes several bubbles with human pacing. Cloudflare Workflows give each of these jobs **durable steps** (`step.do`) with retries and timeouts and **durable sleeps** (`step.sleep`), so the work continues when the app is closed and resumes after failures without repeating completed steps.

```jsonc [apps/api/wrangler.jsonc]
"workflows": [
  { "name": "wildcard-onboarding", "binding": "ONBOARDING_WORKFLOW", "class_name": "OnboardingWorkflow" },
  { "name": "wildcard-chat", "binding": "CHAT_WORKFLOW", "class_name": "ChatWorkflow" }
]
```

Workflow names are account-wide: an independent installation must pick its own names while keeping the bindings and class names. Wrangler creates or updates both Workflows and the Cron Trigger during the normal API release.

## `ChatWorkflow`

`apps/api/src/chat/workflow.ts` routes by payload kind:

| Kind | Handler | Started by |
| --- | --- | --- |
| Private turn (default) | Reply pipeline | `POST …/chat/turns` → `dispatchAgent` |
| `group` | Group reply round (`groups/workflow.ts`) | Group messages, requests, welcomes |
| `initiative` | Proactive messages and re-engagement (`chat/initiative.ts`) | Cron `dispatchInitiatives` |
| `welcome` | A new contact's first message (`chat/welcome.ts`) | Cron `dispatchContactWelcomes` |
| `home` | For you curation (`home/workflow.ts`) | Cron `dispatchHome` or `/api/v1/home/refresh` |
| `home-comment` | Contact replies to For you comments | Comment creation |

Task work turns, schedules and page-monitor wake-ups also run as `CHAT_WORKFLOW` instances.

### Main steps of a private reply

`select-account-model` → `check-attention` → `attended-chat` (short connect delay) → wait for the composer → `batch-consecutive-messages` → `mark-running` → `read-delay` → `mark-read` → optional `transcribe-voice` → memory refresh → `prepare-reply` (up to 2 retries, 8 minute timeout) → `reply-timing-decision` → for each bubble `compose-message-N`, optional `voice-message-N`, `publish-message-N` → `deliver-push` → memory refresh → `review-conversation-learning` → `release-attention` → presence idle.

Instance IDs are deterministic (for example `chat-<turnID>-a1`) and registered in `chat_workflow_instance` before creation, so recovery can always find, retry or clean them up.

### Attention

An agent handles one item at a time across all of its private chats and groups. `agent_attention` stores an atomic claim, enforced by a trigger; when a Workflow finishes, `release-attention` dispatches the next queued item. The Cron releases abandoned claims.

## `OnboardingWorkflow`

Started with ID `onboarding-<owner>` after sign-up (`POST /api/v1/onboarding`):

1. `load-preferences` and `generate-identities` (Muse Spark plans five contacts).
2. `adult-birthday-plan` and `publish-contacts` (contacts appear immediately with `setup_pending = 1`).
3. Parallel `adult-portrait-N-*` steps generate portraits with `muse-image-1.0` into R2, with a `ready-without-portrait` fallback.
4. `publish-circle` creates the optional Friends, Study or Work group and completes onboarding.

The same class runs **AI contact generation** jobs when the payload carries a `generationID`.

## The minute Cron

`* * * * *` calls `scheduled()` in `apps/api/src/index.ts`. Every duty runs in `ctx.waitUntil` and is idempotent.

| Group | Duties |
| --- | --- |
| Recovery | `recoverOnboarding`, `recoverContactGeneration`, `recoverChats` (reconcile turns with Workflow status, up to 50 per run), `recoverGroups` |
| Dispatch | `dispatchSchedules`, `dispatchTasks`, `dispatchMonitors`, `dispatchHome`, `dispatchInitiatives`, `dispatchContactWelcomes`, `dispatchWelcomes`, `dispatchGroupRequests` |
| Delivery | `deliverPush` (APNs/Web Push outbox), `deliverGroupPush`, `deliverRemoteNative` |
| Cleanup | `cleanResources` (R2 and Workflow outbox), `cleanAttachments`, `cleanOAuthFlows`, `prunePersonalityEvents` (60 days), `pruneLearning`, `expirePresence`, `expireLinkPreviews` |

Energy has no Cron duty: balances are recharged lazily when a group admission checks them.

## Failure handling

- Known model errors (`MODEL_*`) trigger a bounded `recover-response` phase; other failures are saved on the turn so the client can offer a retry (`POST …/turns/:turnID/retry`).
- Started tools keep their receipts, so retries do not repeat side effects.
- Workers Logs show sanitized events only. Already-running instances keep the code version and model they started with.
