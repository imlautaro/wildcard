## Configuration

```jsonc [apps/api/wrangler.jsonc]
"d1_databases": [
  {
    "binding": "DB",
    "database_name": "wildcard-db",
    // Local development only; releases look the database up by name.
    "database_id": "00000000-0000-0000-0000-000000000000",
    "migrations_dir": "migrations"
  }
]
```

The versioned `database_id` is a placeholder used only by local development. At release time the database is found by name (`WILDCARD_DB_NAME` overrides `wildcard-db`) in the target account, created on the first release, and its real ID is written to the ignored `apps/api/wrangler.release.json`. `npm run infra:provision` shows it (and `-- --create` creates it) without deploying.

Everything the product stores lives in this one SQLite database: accounts and sessions, contacts, chats, groups, memory, tasks, documents, mini apps, connectors, the For you feed, outboxes and admin settings. Timestamps are milliseconds.

## Access pattern

- **Raw SQL.** The API uses `env.DB.prepare(...)`, `.bind()` and `env.DB.batch([...])` with hand-written SQL. Drizzle (`src/db/schema.ts`) is used only by the Better Auth adapter.
- **Atomic batches and guards.** Publication, attention claims and history revisions rely on conditional `INSERT … SELECT` / `UPDATE … WHERE` statements inside batches rather than application locks.
- **Triggers.** Several invariants are enforced by triggers, for example registering Workflow instances (`register_private_workflow`) and filling the `resource_cleanup` outbox when rows are deleted.
- **Compound SELECT limit.** D1 caps compound `SELECT` statements at five terms; validate unusual SQL against local `workerd` D1 (see the static checks in `scripts/checks/`).

## Migrations

- `apps/api/migrations` holds **93** sequential files, from `0001_auth.sql` to `0093_privacy_controls.sql`.
- Migrations are additive and forward-only. **Never rewrite an applied migration.** A Worker rollback does not undo D1 changes, so each migration must stay compatible with the currently active Worker.
- Local: `npm run auth:setup:local` (first time) or `npm run db:migrate:local`.
- Production: the API release script runs `wrangler d1 migrations apply DB --remote` **before** uploading the new code. There is no separate manual migration step.

See [Database migrations](/en/operations/database-migrations) for the workflow to add one.

## Full-text search

Contacts search past conversations with SQLite **FTS5** virtual tables (`chat_turn_search` from migration 0007, `group_message_search` from 0019). Memory selection is lexical by default; optional semantic ranking stores Workers AI embeddings in D1 itself (migration 0057) instead of using Vectorize.

## Rate limits in D1

Auth endpoints use fixed one-minute buckets keyed by a SHA-256 of `ip:path:bucket` in `auth_rate_limit`, with the client IP from `CF-Connecting-IP`. The same helper limits other actions per user (for example chat generation at 20 per minute). Exceeding a limit returns `429`.

## Cleanup outbox

Deleting a chat, contact, group or account cannot synchronously remove R2 objects and Workflow instances. Instead, D1 triggers enqueue rows in `resource_cleanup` (migration 0063, scoped by 0064). The minute Cron's `cleanResources` drains it with retries and backoff. The lifecycle tests in `apps/api/tests` cover these paths.

## Inspecting the database

```bash [Terminal]
# Local database
cd apps/api && npx wrangler d1 execute DB --local --command "SELECT COUNT(*) FROM user"
```

::caution
Do not query production data to validate features. Use fictional local data. In this installation, `wrangler d1 … --remote` is not authorized for the local Wrangler login; remote migration state is inferred from a successful API release.
::
