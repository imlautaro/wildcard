## Writing a migration

1. Create the next file in `apps/api/migrations`, for example `0094_my_feature.sql`. Numbers are sequential and names describe the change.
2. Write plain SQLite. Prefer **additive** changes: new tables, new nullable or defaulted columns, new indexes and triggers.
3. Keep it compatible with the Worker version that is currently active: the migration runs **before** the new code is uploaded, and old code must keep working against the new schema during the release and after a code rollback.
4. Never edit a migration that has already been applied anywhere.

```sql [apps/api/migrations/0094_example.sql]
-- Additive: older code ignores the new column.
ALTER TABLE contact ADD COLUMN example_flag INTEGER NOT NULL DEFAULT 0;
CREATE INDEX IF NOT EXISTS contact_example_idx ON contact(user_id, example_flag);
```

## Validating locally

```bash [Terminal]
npm run db:migrate:local            # apply pending migrations to the local D1
npm run test:lifecycle              # cleanup, deletion and isolation regression tests
```

- D1 caps compound `SELECT` statements at five terms; check unusual SQL against local `workerd` D1.
- `scripts/checks/*-sql-compile.*` scripts statically compile the SQL used by several features.
- If a migration adds rows that must be deleted with their owner, extend the `resource_cleanup` triggers and the lifecycle tests.

## Shipping

Commit and push. The API release applies pending migrations with `wrangler d1 migrations apply DB --remote` and only then deploys the code. The release migrates the database resolved into `apps/api/wrangler.release.json`; there is no separate command to migrate production by hand.

## Documenting

Every migration that adds a service, permission or behavior must be described in `docs/infrastructure.md` (setup, verification, rollback and data compatibility) and in the feature guide. The guides reference migrations by number (for example "migration 0093").
