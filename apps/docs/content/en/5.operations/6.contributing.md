The binding rules are in `AGENTS.md` at the repository root. This page summarizes them.

## Working agreements

- **English** for code, identifiers, team-authored strings, documentation, comments and commit messages. User-facing copy is localized to Spanish on iOS, web and the marketing site; this docs site is the explicit bilingual exception.
- Keep the native app in `apps/ios`, the web app in `apps/web` and the API in `apps/api`. JavaScript dependencies use npm workspaces and the root lockfile.
- **Every product change ships on both iOS and web** in the same change, with matching behavior, copy and caching rules, and with [`docs/web.md`](/en/reference/web) and the feature guides updated. Only ship to one client when explicitly scoped or when a platform limitation prevents it, and document that limitation.
- Do not copy code, assets, configuration, credentials or history from the archived project.
- Builds and tests run when requested; static validation is always allowed.
- Every service or infrastructure change includes versioned configuration and updates to [`docs/infrastructure.md`](/en/reference/infrastructure), the README and affected setup guides, so an independent account can reproduce the whole project: prerequisites, permissions, creation order, bindings, account-specific replacements, secret names (never values), local development, migrations, release, verification and rollback. State unverified steps.
- Never commit credentials, generated files or local Xcode user settings.
- Production releases come only from committed and pushed source through automatic deployment.

## Cache by default

Every network-backed feature is designed with a **session-owned cache** before its views are wired:

- Reuse loaded data synchronously on navigation (including empty results); block only on the first load. Revalidate in the background and keep content visible through transient failures.
- On iOS reuse the conversation stores, `NavigationSnapshotCache` and `PrivateImageCache`; never add view-local downloads or a parallel image cache. Image keys include account isolation, access context, resource identity and version.
- Document freshness, refresh, mutation updates and invalidation, request deduplication, stale-response rejection, pagination, budgets and eviction. Preserve pending submissions and idempotency IDs across navigation.
- Invalidate on deletion, access loss and account changes; reject late responses. Cached permissions never replace server authorization.
- Record cache behavior and device verification steps in the feature guide and [`docs/caching.md`](/en/reference/caching).

## Checklist for a feature

1. API route and migration in `apps/api` (additive, compatible with the active Worker).
2. iOS and web implementations with the cache rules above, in English and Spanish.
3. Feature guide in `docs/`, [`docs/web.md`](/en/reference/web), [`docs/caching.md`](/en/reference/caching) and, for infrastructure, [`docs/infrastructure.md`](/en/reference/infrastructure).
4. Watch paths in `docs/workers-build-paths.json` and the dashboard if new cross-directory dependencies appear.
5. Type checks (and tests when requested).
6. Update this documentation site (`apps/docs/content/en` **and** `apps/docs/content/es`) when architecture, configuration or operations change.
